# コミットメッセージルール

## 基本フォーマット

<type>: <subject>

- type: 変更の種類
- subject: 変更内容（日本語 OK、短く具体的に）

### 記述例

feat: ログ画面に月フィルタを追加
fix: todayEventsの時刻をUTC解釈に統一
chore: composeのマウント先をbackend/frontendへ更新
docs: コミットルールを追加

---

## Type（変更の種類）

優先度の高い順に記載しています。
迷った場合は、ユーザー影響が一番大きいものを選びます。

| Type     | 説明                                   | 使用例                                           |
| -------- | -------------------------------------- | ------------------------------------------------ |
| feat     | ユーザー向けの機能追加・変更           | UI の新機能、API エンドポイント追加              |
| fix      | ユーザー向けの不具合修正               | 500 エラー修正、表示崩れ修正、集計ズレ修正       |
| perf     | パフォーマンス改善                     | クエリ最適化、キャッシュ追加、レスポンス速度改善 |
| refactor | リファクタリング（挙動は変えない）     | ロジック整理、責務分割、命名改善                 |
| test     | テストコードの追加・修正               | Feature テスト追加、fixture 更新                 |
| docs     | ドキュメントの更新                     | README、設計メモ、運用手順、API 仕様書           |
| style    | コードスタイルの修正（挙動は変えない） | prettier 適用、インデント、lint 対応             |
| chore    | ビルドやツール設定など                 | ツール設定、依存更新、開発用スクリプト修正       |

---

## Subject（件名）の書き方

### 良い書き方

- 日本語で OK
- できるだけ短く、具体的に
- 何をどうしたかが伝わる表現
- 末尾の句点は付けない
- 変更対象（frontend / backend / db など）は文面で分かるように書く

例:

fix: フロントの設定保存時エラー表示を改善
refactor: dashboard集計のクエリ生成を整理
docs: backend API仕様の補足を追加

### 避けたい書き方

fix: 修正
feat: いろいろ

---

## Breaking Change（互換性が壊れる変更）

API のレスポンス形式変更、URL 変更、データベーススキーマ変更など、
互換性が壊れる場合は必ず「!」を付けます。

記述例:

feat!: dashboard APIのレスポンス形式を変更
fix!: usersテーブルのemailカラムをunique制約に変更

---

## Breaking Change の本文ルール

Breaking Change を含む場合は、本文に以下を必ず記載します。

- 何が壊れるのか
- 影響範囲
- 移行手順や対応方法

本文例:

feat!: dashboard APIのレスポンス形式を変更

BREAKING CHANGE:

- レスポンスのitemsがdata配下に移動
- 旧: { items: [...] }
- 新: { data: { items: [...] } }

影響:

- dashboardを利用する全フロント画面

対応:

- フロント側のレスポンス処理を修正済み
