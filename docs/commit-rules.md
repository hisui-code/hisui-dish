# コミットメッセージルール

## 基本フォーマット

```
<type>(<scope>): <subject>
```

- **type**: 変更の種類
- **scope**: 影響範囲（対象ディレクトリや領域）
- **subject**: 変更内容（日本語 OK、短く具体的に）

### 記述例

```
feat(frontend): ログ画面に月フィルタを追加
fix(backend): todayEventsの時刻をUTC解釈に統一
chore(infra): composeのマウント先をbackend/frontendへ更新
docs(docs): コミットルールを追加
```

---

## Type（変更の種類）

優先度の高い順に記載しています。迷った場合は上位のものを選びます。

| Type         | 説明                                   | 使用例                                           |
| ------------ | -------------------------------------- | ------------------------------------------------ |
| **feat**     | ユーザー向けの機能追加・変更           | UI の新機能、API エンドポイント追加              |
| **fix**      | ユーザー向けの不具合修正               | 500 エラー修正、表示崩れ修正、集計ズレ修正       |
| **perf**     | パフォーマンス改善                     | クエリ最適化、キャッシュ追加、レスポンス速度改善 |
| **refactor** | リファクタリング（挙動は変えない）     | ロジック整理、責務分割、命名改善                 |
| **test**     | テストコードの追加・修正               | Feature テスト追加、fixture 更新                 |
| **docs**     | ドキュメントの更新                     | README、設計メモ、運用手順、API 仕様書           |
| **style**    | コードスタイルの修正（挙動は変えない） | prettier 適用、インデント、lint 対応             |
| **chore**    | ビルドやツール設定など                 | ツール設定、依存更新、開発用スクリプト修正       |

---

## Scope（影響範囲）

基本は「どこを触ったか」が一目で分かる粒度にします。

### 推奨スコープ

| Scope             | 対象                                          |
| ----------------- | --------------------------------------------- |
| `frontend`        | フロント（Vite + React）                      |
| `backend`         | バックエンド（Laravel）                       |
| `backend-archive` | 退避した Rails 側                             |
| `infra`           | Docker / Compose / Makefile / DevContainer 等 |
| `db`              | migration / schema / seed 等                  |
| `docs`            | ドキュメント領域全般                          |
| `rpi`             | Raspberry Pi 側                               |

### Scope の省略について

**基本的に scope は必須**ですが、以下の場合のみ省略可能です：

- リポジトリ全体に影響する変更（依存関係の一括更新など）
- 複数の scope に跨り、どれか 1 つに分類できない場合

**省略例:**

```
chore: リポジトリ全体の依存更新
docs: プロジェクト全体のREADME更新
```

> ⚠️ 迷った場合は、最も影響の大きい scope を 1 つ選んで付けることを推奨します。

## Subject（件名）の書き方

### ✅ 良い書き方

- 日本語で OK
- できるだけ短く、具体的に
- 「何をどうしたか」が伝わる表現
- 末尾の句点は付けない

**良い例:**

```
fix(frontend): 設定保存時のエラー表示を改善
refactor(backend): dashboard集計のクエリ生成を整理
```

### ❌ 避けたい書き方

```
fix: 修正
feat: いろいろ
```

## Breaking Change（互換性が壊れる変更）

API のレスポンス形式変更、URL 変更、データベーススキーマ変更など、互換性が壊れる場合は **必ず** `!` を付けます。

**記述例:**

```
feat(backend)!: dashboard APIのレスポンス形式を変更
fix(db)!: usersテーブルのemailカラムをunique制約に変更
```

**本文に必須の情報:**

- 何が壊れるのか
- 影響範囲
- 移行手順や対応方法

**本文の例:**

```
feat(backend)!: dashboard APIのレスポンス形式を変更

BREAKING CHANGE:
- レスポンスのdataフィールドがネストされた構造に変更
- 旧: { items: [...] }
- 新: { data: { items: [...] } }

影響: フロントエンドの全dashboard関連コンポーネント
対応: frontend側でレスポンス処理を修正済み
```

## 旧ルールからの移行

以前の `WEB:` / `API:` / `RPI:` プレフィックスは以下のように置き換えます：

| 旧ルール | 新ルール                               |
| -------- | -------------------------------------- |
| `WEB:`   | `*(frontend):`                         |
| `API:`   | `*(backend):` / `*(db):` / `*(infra):` |
| `RPI:`   | `*(rpi):`                              |
